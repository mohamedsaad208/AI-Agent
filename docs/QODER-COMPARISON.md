# مقارنة: AI Code Engineer (تولنا) مقابل Qoder

تاريخ المقارنة: 2026-09-24 — بعد تدقيق أمني UI 2.5 و192 اختبارًا ناجحًا حتى UI 2.7. التغيير في UI 2.7 طبقة عرض فقط (صفحة ويب محلية تخدمها المكتبة القياسية)، وقدود المقارنة أدناه لم تتأثر.

## ١. الخلاصة

Qoder **وكيل عام** يقرأ ويكتب وينفّذ ويوزّع مهامًا على subagents مع ذاكرة دائمة.
تولنا **بوابة مراجعة** لموديل محلي صغير: لا يكتب ملفًا ولا يشغّل أمرًا إلا بعد موافقة صريحة مربوطة ببصمة، ويثبت أن الاختبار جرى فعلًا.

القوة النسبية ليست في الذكاء، بل في **من يملك حق القرار**: في Qoder الموديل يقترح والشارح يوافق على صلاحيات، وفي تولنا الموديل لا يملك أصلًا قناة كتابة.

## ٢. جدول القدرة

| القدرة | تولنا | Qoder |

| حلقة الوكيل | JSON actions مغلقة: `list_files` / `read_file` / `search_code` / `propose` / `blocked` — فعل واحد لكل دورة | أدوات حرة (Read/Grep/Edit/Bash/Agent/Web…) مع اختيار الأداة بحسب المهمة |

| الأمان | review-first + رفض 8.3 aliases + ملفات تعليمات الأدوات للقراءة فقط + تنقية المخرجات من المفاتيح + loopback فقط | permission modes، hooks، worktrees، approvals — أوسع سطحًا لأنه أعطي صلاحيات أعرض |

## ٣. تقسيم التسكات والتتابع: التشريح الدقيق

**ما هو موجود فعلًا (مثبَّت باختبارات):** داخل المهمة الواحدة التتابع صارم —
`DISCOVERING → WAITING_APPROVAL → APPLIED_UNVERIFIED → run → CHECKS_PASSED | VERIFICATION_FAILED | VERIFICATION_BLOCKED`.
لا يُقبل `record_run` قبل Apply، ولا `Run` إلا من حالة مطبَّقة، وكل جولة إصلاح تنتهي بمقترح يُراجع من جديد، والمدار محدود بـ`MAX_FIX_ROUNDS = 3`.

**ما كان ناقصًا وأُغلق في هذا الجولة:** التتابع **بين** المهام. لم يكن شيء يمنع مهمة ثانية فوق ملفات مهمة أولى لم يُختبر قط. الآن `unverified_prior_task` يقرأ آخر جلسة في نفس الـchat ويعلن الحالة في المحادثة، وحالتا `PARTIAL_APPLY`/`APPLYING` (apply مقطوع) تتطلآن موافقة صريحة قبل أي تخطيط جديد.

**الفجوة التي كانت متبقية — أُغلقت في UI 2.6:** لم يعد التتابع بين المراحل من صنع الإنسان. `planbook.py` يحوّل عناوين `plan.md` المرقّمة إلى **ledger** (حدّ أقصى ١٢ خطوة) محفوظ في `<app data>/.agent-plans/` **خارج** المجلد المعتمد، فلا يستطيع أي مقترح تعديل البوابة التي تتحكم فيه؛ والمفتاح هو بصمة الخطة، فتغييرها يبدأ سجلًا جديدًا بدل توريث الأحكام. خطوة «موثَّقة» لا تصبح كذلك إلا بوصول جلسة مرتبطة بها إلى `CHECKS_PASSED` مع **إثبات من تقارير الاختبارات** (JUnit XML لـMaven/Gradle أو `--junitxml` لـpytest، بطابع زمني بعد بداية التشغيل) — الصفر بلا اختبار منفَّذ يُبقي الخطوة مفتوحة ويذكر السبب. بعد التوثيق يبدأ تلقائيًا تشغيل **تخطيط** الخطوة التالية، والموافقة على الكتابة تبقى يدوية، و`reopen()` يعيد فتح الخطوة عند Roll back. التقدم ظاهر في شريحة `plan.md — step 1/3` وفي سطر Settings.

**إثبات الاختبارات مستقل الآن:** `decide_status()` يجعل التقرير أعلى من كود الخروج؛ إخفاق في XML يعني `failed` حتى لو ابتلع الـbuild الإخفاق، والعدّ من السطر النصي صار احتياطًا للوصفات التي لا تكتب تقريرًا.

## ٤. ما لا يحتاجه تولنا

نسخ subagents العامة، أو Bash مفتوح، أو الكتابة بلا مراجعة: كل واحد منها يلغي السبب الوحيد الذي يجعل Tool محلي صغير مقبولًا على مشروع حقيقي.
